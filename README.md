# multipackage-release-planner

离线版本发布规划工具：读取一批包的当前版本和按时间排列的提交，根据约定式提交
(Conventional Commits) 计算每个包的新版本并生成变更记录。工具**只生成计划**，
不修改仓库、不调用任何发布服务。仅使用 Go 标准库。

## 用法

```sh
go run . [-in input.json] [-format json|markdown|all]
```

- `-in`：输入 JSON 文件，缺省从标准输入读取。
- `-format`：输出格式，`json`（默认）、`markdown` 或 `all`（两者都输出到标准输出）。

## 输入格式

```json
{
  "packages": [{"name": "core", "version": "1.2.3"}],
  "commits": [
    {"id": "abc123", "message": "feat(core): add thing", "packages": ["core"]}
  ]
}
```

- 版本必须是三段非负整数，不含前导零（如 `0.0.0`、`1.2.3`；`1.0`、`01.0.0` 非法）。
- 每条提交有唯一 `id`、原始 `message` 和显式的影响包集合 `packages`（非空）。
- 提交按时间先后排列。未知包、重复提交 id、重复包名或非法版本都会拒绝整批输入。

## 提交消息格式

首行：

```
type[(scope)][!]: description
```

- `type`：小写英文字母（如 `feat`、`fix`、`chore`）。
- `scope`：可选，非空，不改变显式的影响包集合。
- `!`：可选，表示破坏性变更。
- 冒号后必须有一个空格和非空说明。

破坏性变更（满足任一）：

- 首行含 `!` 标记；
- 正文中独立一行以 `BREAKING CHANGE: ` 开头且说明非空。

正文中普通引用该词（如说明文字里提到）不算破坏性。任何类型的提交都可以是破坏性的。

## 版本规则

- 破坏性变更提升主版本，`feat` 提升次版本，`fix` 提升修订版本，其他类型不提版本。
- 每个包只采用本批最高级别，低位归零；零主版本遵循同一规则（`0.9.0` 破坏性 → `1.0.0`）。
- 没有变更的包保持原版本。

## 输出

- JSON 计划：按包名排序，每个包给出当前版本、新版本、提升级别及分组（major /
  minor / patch）的提交依据，组内保持原提交顺序，同一提交不重复出现。
- Markdown 变更记录：同样的分组与顺序，破坏性提交带 `BREAKING` 标记。
